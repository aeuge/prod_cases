# Пропажа разделяемой памяти PostgreSQL: No such file or directory

> **Кейс:** production-база PostgreSQL начала сыпать ошибками при параллельном выполнении запросов.

> **Симптом:** `ERROR: could not open shared memory segment "/PostgreSQL.2002127633": No such file or directory`

> **Причина:** `systemd` принудительно удалял IPC-объекты при завершении пользовательских сессий из-за параметра `RemoveIPC=yes`.

> **Решение:** отключение `RemoveIPC` на уровне `systemd-logind`.

Короткая заметка о том, как системные настройки ОС могут незаметно "убивать" запросы в базе данных.

---
## 1. Симптомы
---

В логах СУБД начали периодически появляться ошибки следующего вида:

```text
2026-04-01 10:00:00.812 MSK pid= host= db=b user= ERROR:  could not open shared memory segment "/PostgreSQL.2002127633": No such file or directory
```

На первый взгляд это выглядит как внутренний сбой PostgreSQL или нехватка ресурсов. Ошибка выстреливает в моменты, когда база пытается использовать разделяемую память (shared memory) для воркеров при параллельном выполнении запросов. СУБД штатно выделяет память, но в произвольный момент времени сегмент бесследно исчезает. При попытке к нему обратиться или удалить его, PostgreSQL ожидаемо возвращает ошибку.

---
## 2. Причина: агрессивный уборщик systemd
---

Виновником "пропажи" памяти оказался системный менеджер `systemd`, а точнее его служба `systemd-logind`. 

Управление ресурсами сессий регулируется параметром `RemoveIPC` в конфигурационном файле `/etc/systemd/logind.conf`. Этот параметр решает судьбу объектов System V и POSIX IPC при завершении сеанса пользователя.

Он может принимать два значения:
* `no` — нормальное поведение (по умолчанию в ванильном systemd). Объекты IPC живут своей жизнью и управляются создавшим их приложением.
* `yes` — объекты IPC агрессивно удаляются ОС при завершении сеанса пользователя (например, при дисконнекте по SSH или завершении cron-задачи).

Чаще всего на эти грабли наступают при установке PostgreSQL из исходных кодов (когда нет пакетных systemd-юнитов, которые могут переопределять поведение) или при использовании кастомных политик безопасности ОС, где `RemoveIPC` включен принудительно. `systemd` просто вычищает ресурсы ОС "за спиной" у PostgreSQL.

---
## 3. Решение
---

Для начала можно проверить, применяется ли удаление IPC к нужным службам (например, для ssh сессий):

```bash
systemctl show --property=RemoveIPC ssh.service
```

Чтобы исправить проблему глобально и запретить `systemd` трогать чужую разделяемую память, нужно изменить конфигурацию `logind`.

1. Открываем файл конфигурации:
```bash
nano /etc/systemd/logind.conf
```

2. Находим (или добавляем) параметр `RemoveIPC` и устанавливаем его в `no`:
```ini
RemoveIPC=no
```

3. Перезапускаем сервис логина:
```bash
systemctl restart systemd-logind.service
```
*(Внимание: перезапуск systemd-logind может привести к разрыву текущих активных SSH-сессий).*

**вывод:** 

Если PostgreSQL жалуется на внезапную пропажу разделяемой памяти, 
не торопитесь крутить `shared_buffers` или `work_mem`. 

Вполне вероятно, что операционная система просто занимается слишком усердной "уборкой".
